The Evolution of Observability: From Legacy to Envoy Sidecars

When dealing with legacy microservices, instrumenting code for observability can be a daunting, sometimes impossible task. What if you could gain deep insights—L7 metrics and distributed traces—without modifying a single line of application code?

Over the weekend, I built a throwaway K3s infrastructure using Multipass VMs on athena (over Tailscale) to demonstrate exactly this. Using the classic Weaveworks Sock Shop as our “archived legacy” narrative, I charted the evolution of observability by incrementally injecting sidecar proxies.

The Roadmap

Our goal was simple: take a completely uninstrumented application and progressively add sidecars to intercept traffic, ultimately reaching a modern observability stack powered by Envoy, Prometheus, and Tempo.

Here is the journey in four phases:

Phase 1: The Baseline

We started with the raw Weaveworks Sock Shop app. I deployed a custom alpine-based load generator running a continuous curl loop to simulate constant user traffic. At this stage, our cluster could only capture basic node-level metrics (CPU and Memory spikes) via Prometheus. We were completely blind to HTTP traffic, error rates, and request durations.

Phase 2: Enter HAProxy

To start gaining L7 visibility, we injected an HAProxy sidecar. Using Kustomize patches (phase2-haproxy), we seamlessly routed traffic through HAProxy. Result: By querying the raw Prometheus UI with a [5m] rolling rate, we successfully captured our first L7 metrics spike under {proxy="http_in"}. We could finally see the HTTP requests flowing into the services.

Phase 3: Stepping up with Caddy2

Rolling back HAProxy, we deployed the phase3-caddy overlay, injecting a caddy:2.7.6-alpine sidecar configured with a concise 6-line ConfigMap (Caddyfile). Result: After a 5-minute continuous load test, Prometheus captured the Caddy HTTP requests intercepted by the proxy. Caddy provided a simpler configuration experience while maintaining solid metric output.

Phase 4: The Envoy Endgame

The ultimate goal. We rolled back Caddy and applied the phase4-envoy patch, injecting the Envoy sidecar directly into the front-end pods. The Envoy configuration (envoy.yaml) routed ingress_http listener stats to Prometheus (port 9901) and gRPC traces to our Tempo OTEL Collector (port 4317).

The Final Result: Envoy flawlessly intercepted the traffic. Not only did we get native HTTP downstream metrics (envoy_http_downstream_rq_total) in Prometheus, but we also achieved Distributed Tracing!

Despite a minor networking hiccup where the OTEL Collector experienced a connection refused from the Tempo pod, a quick stabilization of the Tempo initialization loop allowed the traces to flow seamlessly. A raw API query confirmed our success:

{"traces":[{"traceID":"17cb1af2cdf651191b21709e9e631d39","rootServiceName":"front-end","rootTraceName":"ingress","startTimeUnixNano":"1778915291475161000","durationMs":1}]}

Conclusion

By adopting a sidecar pattern, we successfully retrofitted a legacy application with a modern, powerful observability stack. No code changes, no redeploying applications—just infrastructure as code and the power of proxy sidecars.
