Hands-Free GitHub Flow: Automating My Blog with CI/CD

April 16, 2026 •3 min read

Table of Contents

    • The Problem: GitHub Auto-Merge Limits
    • The Fix: Fine-Grained PATs in the Test Suite
    • Conclusion

I recently revamped the publishing pipeline for my Hugo blog. I wanted a robust GitFlow setup—isolating new posts in feature branches, running automated tests against a staging develop branch, and finally releasing to main—without ever touching a Git command manually.

There is a misconception that you need a massive Enterprise budget or a dedicated DevOps team to build a touchless pipeline. That is not true. Small, freelance, and indie developers can completely automate their workflows using free CI/CD tools and local AI agents.

Here is exactly how I built this completely hands-free architecture, and how I bypassed GitHub’s restrictions on free private repositories.

The Problem: GitHub Auto-Merge Limits

My original plan was to use GitHub’s Native Auto-Merge. The idea was simple: apply a merge-when-passing label, let the tests pass, and let GitHub handle the rest.

Unfortunately, Native Auto-Merge is completely blocked on free private repositories.

My next attempt was a custom GitHub Action that listened for labels and used the GitHub CLI (gh pr merge) to merge automatically. While functional, managing the custom event triggers and tokens felt clunky and fragile.

The Fix: Fine-Grained PATs in the Test Suite

Instead of fighting with labels or native limitations, I decided to embed the merge logic directly into the testing phase.

Here is the final automated architecture:

  1. Feature Branches: Every new post gets its own isolated branch (e.g., blog-post/hands-free-github-flow). I write the Markdown, and then I hand off the Git operations to Hermes, my local terminal AI agent. Hermes automatically pushes the branch and triggers the GitHub CLI to open a Pull Request to develop:
    gh pr create --base develop --head blog-post/hands-free-github-flow \
  --title "Add new post: Hands-Free GitHub Flow" \
  --body "Automated feature PR."
  2. Automated Testing (Playwright): To ensure the site builds correctly and there are no broken links, I use Playwright. A GitHub Action (playwright.yml) triggers on the PR, installs Hugo, builds the site, and runs my E2E test suite.
  3. The Auto-Merge Step: Right at the end of the playwright.yml workflow, there is a custom shell step. The exact second the Playwright tests successfully pass, the pipeline authenticates using a Fine-Grained Personal Access Token (stored as the secret BOT_PAT) and executes gh pr merge directly.
  4. Deployment: Because the BOT_PAT auto-merge is incredibly fast, Hermes schedules a local cron job in my terminal. Five minutes after the feature PR is opened, Hermes checks the merge status and executes the final Release PR to move develop into main (production):
    gh pr create --base main --head develop \
  --title "Release: Update Main from Develop"
    Once this PR merges, it triggers the deploy.yml Action, which does a final hugo --minify build and deploys the static files straight to StaticVish.github.io.

Conclusion

This means my GitFlow strategy is genuinely touchless. I act as the architect and the author, but I treat my terminal AI as a DevOps assistant to abstract away the repetitive Git operations. Hermes handles the local branch pushing and PR creation, while GitHub Actions and my BOT_PAT handle the testing and merging in the cloud. From idea to published post, I just get to enjoy writing!
