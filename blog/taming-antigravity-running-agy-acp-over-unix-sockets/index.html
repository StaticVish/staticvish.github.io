Taming Google Antigravity: Running agy acp Over UNIX Sockets Across Multiple Agent Harnesses

Google’s Antigravity CLI (agy) is one of the most capable developer agents available right now. Running on an Antigravity or Google One Pro tier, it gives you direct access to Gemini 4 Argon, Gemini 4 Hydrogen, Gemini 3.8 Flash, and Claude 5.5 without meter-draining API bills.

The trouble begins the moment you try to take Antigravity outside of an interactive desktop terminal.

If you attempt to orchestrate agy inside autonomous agent subagents, CI/CD runners, cron jobs, or headless container environments, you hit a concrete wall: the headless OAuth and keyring deadlock.

Here is how I solved this by daemonizing agy acp over a local UNIX domain socket, and how I drive it across four different agent and editor harnesses.

The Problem: The Headless Keyring Trap & The SDK Disconnect

Antigravity CLI was built as a human-facing desktop tool. Its authentication architecture reflects that:

  1. OS Keyring Dependency: On Linux, agy stores and retrieves OAuth session tokens via the Secret Service API over DBus (org.freedesktop.secrets). On macOS, it uses Keychain; on Windows, Credential Manager.
  2. Headless Deadlock: Subagents (like those spawned via autonomous agent task delegation or background worker pools) run in isolated subprocesses. They lack an active DBUS_SESSION_BUS_ADDRESS and an interactive TTY. When a cold agy process spawns in this environment, it cannot reach the keyring. Instead of cleanly failing, it hangs waiting for browser sign-in or prompts for an auth code on a dead stdin.
  3. The SDK Dead End: When Google recently published the google-antigravity Python SDK, many assumed it would bridge CLI sessions to code. It does not. The SDK strictly accepts developer API keys (GEMINI_API_KEY) or GCP Vertex AI Application Default Credentials. It completely lacks consumer OAuth support.

In fact, Issue #20 on the google-antigravity/antigravity-sdk-python repository (“Support Google Account OAuth and reuse of CLI authentication file”) is an active community issue. Even if you manually extract the Bearer token from Keychain and pass it via custom headers, the SDK rejects it: the Python SDK targets the public API endpoint (/v1beta/models/...), whereas consumer agy subscriptions authenticate against Google’s internal Cloud Code service (daily-cloudcode-pa.googleapis.com/v1internal:...).

Spawning cold agy CLI processes inside subagents was out. Burning per-token API credits via the SDK was unacceptable. The solution had to leverage the existing, authenticated CLI session on the host.

The Protocol: Enter ACP (Agent Client Protocol)

Tucked inside agy is a subcommand: agy acp.

ACP (Agent Client Protocol) is an open JSON-RPC 2.0 protocol designed for agent-to-tool and editor-to-agent communication. Instead of scraping ANSI terminal output or wrestling with PTY escape sequences, ACP provides a clean, bidirectional RPC wire format over stdio:

  • Lifecycle: initialize establishes protocol version and client capabilities.
  • Session Management: session/new initializes a stateful workspace session bound to a directory (cwd), returning a unique sessionId.
  • Execution & Streaming: session/prompt submits tasks and streams back fine-grained events (agent_message_chunk, tool_call, tool_call_update) until the final turn envelope arrives.

Because agy acp handles all model interaction and internal tool calls under the hood, running it once on the authenticated host eliminates every keyring issue.

The Architecture: Daemonizing agy acp Over UNIX Sockets

Instead of launching a heavy, cold agy instance inside each subagent (~400MB RAM each, plus startup latency), I run a persistent host bridge service managed by systemd.

1. The Systemd User Unit

The bridge runs under a systemd user instance at ~/.config/systemd/user/antigravity-acp.service:

[Unit]
Description=Antigravity ACP Socket Bridge Service
After=default.target

[Service]
Type=simple
ExecStart=/usr/bin/python3 %h/.local/bin/antigravity-acp-bridge
Restart=always
RestartSec=3
Environment="PATH=%h/.local/bin:/usr/local/bin:/usr/bin:/bin"
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=default.target

Using systemd’s %h specifier automatically expands to the active user’s home directory. Because systemd runs this within the user’s active login session, antigravity-acp-bridge has ambient access to the desktop keyring.

2. The Socket Multiplexer (antigravity-acp-bridge)

The bridge script resolves $XDG_RUNTIME_DIR (falling back to ~/.cache), listens on antigravity-acp.sock with strict 0600 permissions, and pipes the RPC streams asynchronously:

import asyncio
import os
import signal
import sys
from pathlib import Path

DEFAULT_SOCKET_DIR = os.environ.get("XDG_RUNTIME_DIR") or str(Path.home() / ".cache")
SOCKET_PATH = Path(DEFAULT_SOCKET_DIR) / "antigravity-acp.sock"
AGY_BIN = os.environ.get("AGY_BIN") or str(Path.home() / ".local/bin/agy")

async def handle_client(client_reader, client_writer):
    # Spawn agy acp with automated tool execution permissions
    proc = await asyncio.create_subprocess_exec(
        AGY_BIN,
        "acp",
        "--dangerously-skip-permissions",
        stdin=asyncio.subprocess.PIPE,
        stdout=asyncio.subprocess.PIPE,
        stderr=asyncio.subprocess.PIPE,
    )

    # Bi-directional stream piping
    c2p = asyncio.create_task(pipe_streams(client_reader, proc.stdin))
    p2c = asyncio.create_task(pipe_streams(proc.stdout, client_writer))

    done, pending = await asyncio.wait([c2p, p2c], return_when=asyncio.FIRST_COMPLETED)
    for task in pending:
        task.cancel()

    if proc.returncode is None:
        proc.terminate()

Driving the Setup with Different Harnesses

With the socket bridge running, any process on the machine can execute Antigravity without environment variables, OAuth credentials, or DBus handles.

Harness 1: The Zero-Dependency CLI (agy-sock)

I wrote a lightweight client CLI wrapper (agy-sock) in standard library Python:

class ACPClient:
    def __init__(self, sock_path=None):
        socket_dir = os.environ.get("XDG_RUNTIME_DIR") or str(Path.home() / ".cache")
        self.sock_path = Path(sock_path or (Path(socket_dir) / "antigravity-acp.sock"))
        self.sock = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
        self.sock.connect(str(self.sock_path))
        self.msg_id = 0

    def send_rpc(self, method, params=None):
        self.msg_id += 1
        payload = {"jsonrpc": "2.0", "id": self.msg_id, "method": method}
        if params:
            payload["params"] = params
        self.sock.sendall((json.dumps(payload) + "\n").encode("utf-8"))
        return self.msg_id

    def initialize(self):
        req_id = self.send_rpc("initialize", {
            "protocolVersion": 1,
            "clientInfo": {"name": "agy-sock", "version": "1.0"}
        })
        return self.wait_for_response(req_id)

Now, any shell script or cron task can drive Antigravity models:

# Run a quick code review on a diff
git diff HEAD~1 | agy-sock -p "Review this patch for memory leaks" -m gemini-4-argon

# Run code refactoring in a specific workspace
agy-sock -p "Extract database queries into a repository pattern" -w ~/projects/backend -m claude-sonnet-5-5

Harness 2: Autonomous Agent Subagents

In multi-agent architectures, an orchestrating agent often delegates code implementations to specialized subagents.

Subagents typically run in isolated sandboxes with scrubbed credentials to prevent token leakage. However, because they run on the same system, they can reach the local UNIX domain socket.

Inside the subagent, executing agy-sock connects to the host daemon instantly:

  • No browser OAuth redirects.
  • No DBus Secret Service collisions.
  • Full access to gemini-4-argon and claude-sonnet-5-5 on the existing subscription quota.

Harness 3: Editor Integration (Zed & Neovim)

Modern editors like Zed have first-class support for ACP. Instead of configuring editor plugins with custom API keys, you can point the editor’s ACP client configuration directly to the local bridge socket:

{
  "agent": {
    "type": "custom",
    "command": "nc",
    "args": ["-U", "/run/user/1000/antigravity-acp.sock"]
  }
}

This unifies the model context, conversation state, and subscription quota across both your terminal agents and your GUI editor.

Production Verification: The 1m 37s Lifecycle Benchmark

To test this setup under real conditions, I exercised it on an automated git workflow: decommissioning an interactive static web app from a repository.

The orchestrator dispatched an autonomous subagent with instructions to:

  1. Connect to the Antigravity ACP socket and verify the JSON-RPC handshake.
  2. Checkout the staging branch.
  3. Remove the target static assets, commit, and push.
  4. Open a Pull Request against the production branch.
  5. Monitor the Playwright E2E CI suite and verify automated release deployment.

Results:

  • Socket Handshake: Verified in 0.4s via agy-sock.
  • Git Operations & PR: Feature PR opened automatically.
  • CI & Deployment: The Playwright test container built the static site, validated layout and readability specs, auto-merged the pull request, and triggered the production deployment.
  • Total Execution Time: 1 minute 37 seconds from initial dispatch to verified HTTP 404 live on edge CDN nodes.

Zero human intervention. Zero credential leakage. Zero auth stalls.

Takeaways

  1. Decouple Auth from Execution: Tools built for interactive CLI use will always fight you in automated pipelines if you spawn them directly. Running the authenticated engine as a host-level user daemon over a UNIX domain socket cleanly separates credential management from execution.
  2. Standardize on Wire Protocols: ACP (Agent Client Protocol) is doing for autonomous agents what LSP did for code intelligence. Writing a thin socket client for ACP gives you a universal adapter that works across subagents, bash scripts, and modern IDEs.
  3. Don’t Wait for SDK Feature Parity: When developer SDKs trail behind CLI capabilities (like the ongoing OAuth limitations in google-antigravity), looking at the underlying process transport often reveals a much faster, cleaner path forward.
