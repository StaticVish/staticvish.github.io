Modernizing Legacy Microservices: The Power of Proxy Sidecars

How do you monitor a legacy application without rewriting its code? The answer lies in the sidecar proxy pattern. By attaching a proxy to your existing containers, you can decouple your observability stack from your business logic.

Over the weekend, I built a local throwaway lab to put this theory to the test. Here is a walkthrough of how I set up a base environment and incrementally added HAProxy, Caddy, and Envoy to achieve full HTTP metrics and distributed tracing.

The Base Environment: Multipass & K3s

Before injecting sidecars, I needed a clean, reproducible infrastructure. I used Multipass to spin up an Ubuntu VM on my local machine and deployed a lightweight Kubernetes cluster using K3s.

This gave me a perfect blank slate. I then deployed the classic Weaveworks Sock Shop as my uninstrumented legacy app.

The Problem: Zero Visibility

For this experiment, I used the Weaveworks Sock Shop—a classic, polyglot microservices e-commerce demo. It consists of multiple independent services (carts, catalogue, orders, payment, shipping) written in different languages like Go, Java, and Node.js.

Manually instrumenting an application like this would require diving into multiple codebases and importing tracing libraries for several different languages. That is exactly the headache the sidecar pattern avoids.

First, I deployed the base app completely unmodified. I added a load generator using an alpine image that ran a constant curl loop to simulate active user traffic.

At this stage, we only had basic node metrics. We could see CPU and memory spikes in Prometheus. We could not see HTTP requests or error rates.

When systems fail, you need to know exactly where and why. Without HTTP-level metrics, troubleshooting becomes a guessing game. You might know a node is out of memory, but you have no idea which user request caused it. We were flying blind.

Stepping Up: HAProxy and Caddy

Before Envoy, I tested HAProxy and Caddy as sidecars.

  1. HAProxy: I added it via Kustomize. We caught our first HTTP metrics in Prometheus using the {proxy="http_in"} query.

To achieve this, I injected an HAProxy sidecar with the following configuration to route traffic to localhost and expose Prometheus metrics on port 8404:

global
  log stdout format raw local0
  maxconn 4096

defaults
  log global
  mode http
  option httplog
  option dontlognull
  timeout connect 5s
  timeout client  50s
  timeout server  50s

frontend http_in
  bind *:8080
  default_backend backend_app

backend backend_app
  server local_app 127.0.0.1:8079 check

frontend stats
  bind *:8404
  http-request use-service prometheus-exporter if { path /metrics }
  stats enable
  stats uri /stats
  stats refresh 10s

(Screen print: Prometheus UI showing HAProxy http_in traffic)

  1. Caddy: I swapped HAProxy for Caddy. It only needed a 6-line Caddyfile. We successfully tracked HTTP traffic during a 5-minute load test.

Here is the entire Caddyfile required to expose metrics on port 2019 and reverse proxy the traffic to the application:

{
    admin 0.0.0.0:2019
    servers {
        metrics
    }
}

:8080 {
    reverse_proxy 127.0.0.1:8079
}

(Screen print: Prometheus UI showing Caddy http request durations)

Both worked well for basic HTTP telemetry. But I wanted more. I wanted distributed tracing.

The Solution: Envoy and Tempo

While HAProxy and Caddy are fantastic tools, Envoy was built from the ground up for cloud-native environments. It natively supports advanced telemetry, making it the perfect fit for a Kubernetes-native observability stack.

I removed Caddy and injected Envoy into the front-end pods. Envoy handles metrics and tracing natively without any heavy plugins.

The Code Changes

To inject Envoy, I patched the Kubernetes deployment. This adds the sidecar container next to the app.

# manifests/overlays/phase4-envoy/deployment-patch.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: front-end
spec:
  template:
    spec:
      containers:
      - name: envoy
        image: envoyproxy/envoy:v1.28-latest
        ports:
        - containerPort: 8080
        - containerPort: 9901 # Admin & Metrics
        volumeMounts:
        - name: envoy-config
          mountPath: /etc/envoy

Next, I configured Envoy. It needs to send metrics to Prometheus and traces to the OpenTelemetry (OTEL) Collector. Here is the cluster configuration from envoy.yaml:

# Snippet of envoy.yaml
admin:
  address:
    socket_address: { address: 0.0.0.0, port_value: 9901 }
static_resources:
  clusters:
  - name: tempo_otel
    type: STRICT_DNS
    typed_extension_protocol_options:
      envoy.extensions.upstreams.http.v3.HttpProtocolOptions:
        explicit_http_config:
          http2_protocol_options: {}
    load_assignment:
      cluster_name: tempo_otel
      endpoints:
      - lb_endpoints:
        - endpoint:
            address:
              socket_address:
                address: otel-collector.observability.svc.cluster.local
                port_value: 4317

The Metrics and Traces

Once Envoy was running, the data started flowing.

1. Prometheus Metrics

Envoy intercepted the traffic. Prometheus scraped the Envoy admin port (9901). We captured native HTTP downstream metrics. The key metric was envoy_http_downstream_rq_total.

(Screen print: Prometheus UI showing a steady climb in Envoy downstream requests)

2. Distributed Tracing (Tempo)

A distributed trace allows us to follow a single user request as it travels through multiple microservices. This is critical for finding latency bottlenecks in complex architectures.

Envoy sent gRPC traces to the OTEL Collector on port 4317. The collector forwarded them to Tempo on port 3200. We fixed a minor initialization bug, and the traces appeared.

(Screen print: Grafana Explore UI showing the trace traces for the front-end ingress)

Conclusion

We added deep observability to a legacy app. We did not write any new application code. We just injected a sidecar and configured the routing. Envoy makes this powerful and scalable.
